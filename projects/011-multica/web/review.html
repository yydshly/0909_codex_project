Multica：完整理解与回顾

2026-09-09 · 源码基线 9d3613653e310bbbed5ae294efd8f405e3b722aa。

本文整合本次讨论、源码与官方文档核对，以及本机真实执行结果。本文区分已有机制、本次实测和扩展建议。经用户确认，研究资料发布到项目研究室；原版应用仍是本机演示实例。

整体理解架构图 · 原版运行验证 · 技术阅读补充 · 项目环境与启动

1. 一句话定位

Multica 是已有 Agent 工具之上的人机协作与执行编排平台：人提出目标、参与评审和控制；组长 Agent 决定分工；平台落实派工与运行管理；Codex、Claude Code 等工具完成实际工作。

主调用链是 Multica → Agent 工具 → 模型。模型提供推理，Agent 工具把推理与读文件、运行命令等动作组成执行循环，Multica 把这些执行组织成有任务记录、分工和反馈的工作流程。

看板只是用户入口之一。工程核心还包括工具适配、持久队列、执行节点连接、运行生命周期和事件驱动交接。

2. 逐项回答我们讨论过的问题

我们的问题 核对后的理解
只是任务管理和下发吗？ 还有实际启动 Agent 工具、接收输出、记录工具事件、处理取消/重试、触发多 Agent 交接和人工反馈。
适配层统一的是模型接口吗？ 主要统一 Agent 工具执行接口。模型、推理强度等选项可以透传，但各工具支持程度不同。
调度模型，还是 Codex、Claude Code？ 主要调度后者。平台里的 Agent 是配置好的执行角色，最终通过相应工具调用模型。
有一个专门调度的 Agent 吗？ 平台派工由程序和数据库执行，不必有调度 Agent。小队模式另外有 Leader Agent 做业务分工判断。
是路由和负载均衡模块吗？ 有执行路由、队列和并发约束；不能据此认定已有按价格/空闲度自动选模型或机器的通用负载均衡。
组长与成员如何对话？ 通过 Issue 评论、结构化提及、平台事件和后续 Run 交接，不自动共享模型会话。
组长一直等成员吗？ 通常委派并记录决策后结束本轮，符合规则的反馈事件再次唤醒它。
本质还是顺序执行吗？ 不是固定串行流水线。独立任务或独立成员可以并行；有依赖的步骤等待前一步，受并发设置、容量与目录锁约束。
是按需调用模型吗？ 平台按需启动或续接 Agent 执行；工具内部可能多次调用模型和工具。一次 Run 不等于一次模型请求。
人下发后还能控制吗？ 可以看过程和结果、评论、指定 Agent、停止 Run、重试、调整负责人、评审和返工。
有“每一步都必须由人批准”吗？ 不能这样理解。工作流评审与底层工具审批是不同机制；默认执行面向无人值守。
产品价值是什么？ 降低协调成本，让多工具、多角色、多人参与的工作可分配、可追踪、可交接、可复查。

3. 核心对象：不要混淆这些层

对象 含义 关系或例子
Workspace / Project 团队与项目组织空间 成员、任务、Agent 和权限的组织范围
Issue 持续存在的工作目标 描述、负责人、评论、附件和验收状态；可以经历多次执行
Run 某个 Agent 的一次执行记录 记录触发原因、排队、运行、结果和日志
Agent（平台角色） 配置好的执行者 名称、职责、指令、Skills、运行环境、模型选项等
Squad / Leader 成员集合与协调角色 组长本身仍由 Agent 工具运行，不是独立模型网关
Runtime / Daemon 执行环境与机器上的运行进程 Daemon 发现工具、连接平台、领取任务并管理进程
Provider / Backend 工具适配实现 将不同工具包装到统一 Execute / Session 接口
Agent 工具 具有执行循环的客户端 Codex、Claude Code 等；管理上下文并调用工具
模型 推理与生成能力 由 Agent 工具调用，不等于整个 Agent
Skill / 插件 / MCP 方法与能力扩展 Skill 复用方法，插件扩展平台，MCP 连接工具/资源

Run completed 仅表示一次执行正常结束；Issue 是否达成目标，要看产物与验收。 同一种工具可以承载多个不同职责的 Agent，小队也可以组合不同工具。

4. 整体架构：两种调度与一条执行链

层次 负责什么 技术和数据
人与业务入口 提目标、派工、讨论、审查、干预；也可从事件触发 Web、桌面/移动端、CLI/API、消息/Git 集成、Autopilot
业务分工 判断交给谁、如何拆解、下一步是什么 人工操作，或 Leader 根据目标、成员职责和 Skills 推理
平台服务 权限、Issue/Run、事件路由、队列、去重、状态、恢复 Go、Chi、sqlc、WebSocket；PostgreSQL；Redis 可选
执行节点 准备目录、上下文与配置，领取任务，启动/取消进程，回传输出 本机或服务器上的 Daemon、并发约束及目录锁
工具适配 对齐启动参数、消息、工具事件、结果、取消和续接 Backend.Execute 返回 Session；具体能力依 Provider 而异
Agent 执行 模型推理与真实工具操作循环 Codex、Claude Code 等；文件、命令、MCP、外部系统

Web 使用 Next.js；Desktop 使用 Electron 并复用业务组件；移动端采用 Expo / React Native。本次只运行 Web、Go 服务、PostgreSQL 和本机 Daemon。

执行链：入口请求 → 检查权限/触发规则 → 创建或安排 Run → 对应 Daemon 领取 → 准备工作目录和指令 → Provider 启动工具 → 输出和结果回传 → 更新界面/触发后续动作。

PostgreSQL 持久化任务队列；领取 SQL 使用 FOR UPDATE SKIP LOCKED 避免并发抢同一行。WebSocket 支持实时通知及 Daemon 通信，轮询路径帮助断线后继续获取工作。并发限制、去重、目录锁和重试处理可靠性问题，不保证业务结果必然正确。

人或 Leader 决定“做什么、交给谁”；平台程序决定请求如何落到实际执行。 单 Agent 任务可以跳过组长，不必强行引入多 Agent。

4.1 顺序、并行和按需调用：三个不同问题

它是按事件触发、支持并发的人机任务编排平台，不是固定顺序执行器。 我们演示的“组长委派 → 成员反馈 → 组长核对”有前后依赖，所以观察起来是顺序交接；这不代表平台只能串行。

范围 如何执行
多个独立 Issue 可以同时有 Run 执行，受节点容量和 Agent/Daemon 并发配置约束
同一 Issue 的多个成员 组长把相互独立的工作交给不同成员时，可并行；依赖别人结果的步骤需等待交接
单个 Agent 工具内部 如何调用模型、读写文件或运行命令，由 Codex/Claude Code 等自身执行机制决定

例如，可让 A 分析后端、B 分析前端，两者独立执行后由组长汇总，再交给人评审。这是可组织的流程，不表示平台自动识别所有依赖、自动把任意任务并行化，也不是本次已实测的并行负载场景。

人提出目标 → 组长拆分
                ├─ A：分析后端 ─┐
                └─ B：分析前端 ─┤ 可并行，受资源约束
                                ↓
                            组长汇总 → 人评审

“按需”作用在平台执行层：任务分配、评论或事件触发一次 Agent 执行；该执行内部可能反复调用模型和工具。不能把“平台安排一次 Run”直接换算成“一次模型调用”，也不能据此认定平台是模型 API 的智能负载均衡器。

5. 组长与成员如何交互

  1. 人创建 Issue，分配给 Squad；平台创建组长 Run。
  2. 执行时给组长注入任务上下文、协作协议、成员名单/角色/Skills 和小队指令。
  3. 组长判断分工，通过 CLI/API 写委派评论，例如 [@开发](mention://agent/UUID) 请修复登录问题并反馈分支。
  4. 平台识别结构化接收者，检查权限、可用性和触发规则，为成员安排 Run。
  5. 组长记录决策并结束本轮；成员可以排队，组长无需持续占着执行等待。
  6. 成员独立工作，将结果、阻塞原因和产物位置写回任务。
  7. 符合规则的评论/活动事件再次唤醒组长，已有待处理执行时可能合并或去重。
  8. 组长读取最新记录，继续委派、请求人处理、记录无需行动，或交给人评审。

界面需要输入 @ 后从候选列表选择接收者，纯文本 @名字 不等于有效提及。结构化 ID 负责“交给谁”，自然语言负责“做什么”。

共享的是任务、评论和明确的产物引用，不自动共享模型隐式推理、完整会话、成员内存或各机器文件。代码跨目录/机器交接，需要分支、PR、附件等明确方式。

创建小队不会自动同时启动全部成员，也不会提高机器并发上限。续接会话受工具、运行环境及失败类型影响。去重和自触发抑制降低重复执行，但不能承诺复杂协作永不循环。

6. 人类如何介入与控制

人是整个流程中的参与者：开始时派工，中途纠偏，结束时验收。

人的动作 实际效果 边界
看执行日志 查看消息、工具调用、错误及进度，运行中可持续更新 可观察不等于逐个批准工具调用
评论、回复、附件 补充背景、问题和修改意见 是否触发 Agent 取决于接收者与路由规则
@Agent / @Squad 安排指定 Agent 执行，或触发小队组长 不因此自动更改任务负责人或状态
小队任务中普通评论 可按规则触发负责协调的组长 显式提及其他参与者时，不一定同时唤醒组长
@人 / @all / 表情 通知人或表达反馈 @all 和表情不会触发 Agent
停止 Run 停止对应的排队或执行工作 改状态、改负责人，甚至将 Issue 标为取消，都不会自动停止已启动 Run
修改任务或重新分配 更新目标与责任归属 不能假设运行中的工具立即收到并遵循新要求；要制止应停止 Run
重试 / 重新运行 安排后续执行 历史 Run 重试使用原执行者；Issue 级重跑使用当前 Agent 负责人，会话/目录处理也不同
审查与返工 检查真实产物，要求补做，决定任务是否完成 Run completed、待评审、人工验收通过不是同一个概念

典型闭环：人提目标 → 组长分工 → 成员执行 → 组长汇总 → 待评审 → 人检查 → 通过或评论返工 → 后续执行。

待评审是业务状态，不自动构成强制权限关卡。Agent 能改任务状态，不能据此认为所有后续动作都必须等人批准。默认无人值守运行会自动处理底层工具审批提示。

若要求“合并/发布/支付前必须经人批准”，应将审批结果与执行权限绑定到具体工具、服务或业务流程；仅写提示词或挂一个状态不足以保证执行阻断。这是扩展方向，本次没有实现这样的强制审批关卡。

停止不会撤销已写文件或已发生的外部操作，恢复和回滚需要按实际产物处理。

7. 产品价值与使用场景

工程价值在于统一工具与组织执行；智能解题主要来自所接入的 Agent 工具、模型、工作方法和工具权限。平台减少复制任务、手动开工具、追问进度和寻找交接记录的协调成本。

场景 组织方式 需要另外具备什么
软件研发 工单 → 开发 → 测试/评审 → 人验收 仓库访问、分支交接、测试和合并规则
故障与 CI 事件 → 分析 → 修复建议/补丁 → 人确认 告警/CI 接入、限定凭证、可验证恢复条件
周期巡检与报告 Autopilot → 数据收集 → 汇总 → 人检查 数据源、重复执行策略和失败处理
团队知识工作 多角色研究/整理 → 交叉检查 → 人审核 来源证据、业务工具和质量标准

这些是适用方式，不表示全部已实测。单人、一次性、很短的任务，直接用一个 Agent 工具可能更省配置。跨多人、多工具、多阶段或反复发生的工作，更容易从记录与协调能力中受益。

衡量收益：验收通过率、返工率、人工介入次数、总耗时、模型费用和维护成本。组长协调也消耗调用与时间；Agent 数量增加本身不是收益。

8. 已有扩展入口与未来方向

已有机制（源码/文档确认，未全部实测）：Issue/项目/成员管理、多个 Provider、Skills、Squad、CLI/API、评论与聊天触发、Autopilot 定时/事件触发、Git/消息渠道集成、插件、自定义面板、HTTP Hook、外部 MCP 服务。

扩展 作用 证据等级
Provider 接新 Agent 工具，统一执行/取消/结果 已读接口；Claude/Codex 已实测
Skills 复用方法、参考资料、脚本 已有入口，未单独实测完整业务 Skill
插件 / MCP / API / Hook 接业务系统、工具、界面和触发源 已有示例，未接真实外部账号
业务验收与人工审批 将测试、证据、审批与执行权限绑定 扩展建议，未实现强制审批
历史知识积累 检索任务与评审，形成可审核经验 扩展建议，不声称已有自动学习系统
效果/成本调度 按成功率、耗时、费用选择执行者/模型配置 扩展建议，不声称已有通用智能负载均衡
执行环境管理 容器/虚拟机、资源限额、凭证和网络范围 扩展建议；本机目录隔离不是安全沙箱

可扩展意义：把“AI 会做某件事”推进到“团队可以持续、可检查地交付这件事”。先围绕具体业务建立触发、执行、验收和反馈闭环，再判断是否需要增加 Agent。

9. 本次真正跑通了什么

已获取源码并构建原版。运行 Web 开发模式、Go 后端、专用 PostgreSQL、独立 Daemon 配置，发现 Claude 与 Codex 两种工具。

验证 实际结果 能证明什么
LAB-1 文件任务 Claude Code 写出 hello-multica.txt，读回并评论；Run completed，Issue in_review 派工、真实写文件、结果回传
LAB-2 小队交接 Codex 组长 → 成员 → 组长，三次 Run completed，Issue in_review 事件驱动委派、反馈及再次唤醒
等待队列 成员在前一执行结束后开始 观察到并发约束与等待，不是负载测试
人工停止 早期一次 Codex 文件执行被手动取消 Run 级取消路径，不是逐工具审批
人工评审入口 两项任务停在待评审，有评论和执行日志 确认入口；尚未实测“用户评论后再返工”完整循环

真实文件包含三行：Multica demo、Agent: Claude Code、17 * 23 = 391。LAB-2 中组长提及成员，成员回写 391 及分解过程，组长再次运行核对。截图、Run ID、时序与文件校验见 运行验证。

问题也保留：初次 Codex 默认模型与 CLI 版本不兼容；改用可用模型后，一次文件补丁过程卡住并被人工取消；文件演示随后人工改交 Claude Code 完成。这不是自动故障切换演示。 Codex 的小队计算协作独立成功。

未验证全部工具、多机、长期稳定性、真实 Git/消息集成、定时自动化、完整插件/MCP 业务和企业权限边界。开发模式首次编译不作为性能基准。这两项 Agent 演示没有推送业务代码、创建 PR 或对外部署应用。

本机入口：研究页 http://127.0.0.1:8011/；原版 http://localhost:3111/multica-lab/issues；API 127.0.0.1:8111；专用数据库 127.0.0.1:5511。环境版本、启停及本机地址绑定补丁见项目 README。

10. 回顾时必须记住的边界

  • 工具适配 ≠ 模型网关。 透传模型参数不等于直接做模型推理或自动挑最低价模型。
  • 业务分工 ≠ 平台排队。 组长做判断，程序落实执行；单 Agent 可以跳过组长。
  • 多 Agent ≠ 共享大脑。 任务是共同交接点，会话与文件需要明确处理。
  • 评论 ≠ 即时中断。 修改意见可触发后续工作；立即制止需停止具体 Run。
  • Run 结束 ≠ 任务验收通过。 必须检查真实产物与质量。
  • 待评审 ≠ 强制审批。 必须经人批准的动作要有执行关卡。
  • 取消 ≠ 回滚。 已发生的动作不自动撤销。
  • 工作目录隔离 ≠ 安全沙箱。 默认权限基于 Daemon 所属系统用户，隔离需由外部环境保证。
  • 本地运行 ≠ 数据全不出机器。 云模型工具可能发送相关上下文，执行记录会回到连接的平台。
  • 源码可得 ≠ 无条件商业使用。 Multica License 由 Apache 2.0 文本与额外条件共同组成。基线条款区分组织内部使用、第三方托管（包括免费服务）、商业嵌入和品牌保留，商业路线应核对原文与授权。
